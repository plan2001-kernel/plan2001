# Plan2001

**Plan2001 is 9front, ported to AMD64, ARM64 and WASM32 while preserving the original 9front operating system, source tree and interfaces as far as practical.** RISC-V64 is an optional future target (future opt), outside the current release and development scope, without an implementation in the current source tree.

This README is the project's authoritative software specification and list of goals. It describes intended behavior, not a claim that every target is already implemented.

## Foundation and source of truth

- **Base system:** current upstream 9front, built from **one locked Git revision**: `upstream/9front.lock` names the canonical source (`git://git.9front.org/plan9front/9front`, branch `front`, with a mirror), the full commit and tree SHA, and that commit's build.9front.org build number and result. Plan2001 is a thin derivative: upstream 9front plus the WASM32 port, UEFI boot and the existing required integrations. Updates are **regular and explicit**: `tools/upstream check` reports a candidate (preferably the newest revision build.9front.org built successfully), `tools/upstream update` rebases the patch stack onto it for review, and only a reviewed lock change is accepted. Ordinary builds never follow a moving branch. Every accepted lock is reproducible from its Git revision of this repository; the former 9front-11952 base is the revision whose lock names 9front commit `602faae9a52f342a40b086d10b23c71c82dd52d7` (and, before the lock, the SHA256-pinned `9front-11952.amd64.iso`). New Plan2001 features are frozen for now: upstream improvements enter with the baseline, local changes stay minimal.
- **Working WASM32 system:** the implementation maintained in `plan2001-kernel/plan2001` on `main` is an existing, functioning 9front port, not a prototype to replace. Preserve its kernel, WebAssembly user programs, process execution, Rio, browser integration, mobile touch behavior, storage, and established functionality. Change its boot path only as required for the common boot architecture.
- **Authoritative native boot:** this repository's `main` branch contains the modern UEFI boot implementation and shared BootInfo ABI. Its implemented EFI/ESP boot path, including boot via GRUB and booting an installed system from its own disk, **must be preserved**, not redesigned or reverted to legacy boot.
- **Repository authority:** `plan2001-kernel/plan2001` on `main`, including its locked upstream revision, patch stack and overlays, is the sole authoritative operating-system implementation. `plan2001-kernel/room` on `main` owns the separate Room application. The archived `plan2001-kernel/kernel` repository is retained only as a historical object-system (GE/O) reference, never as a boot, kernel or build dependency. The former `userland`, `plan9-wasm32` and `monolith` repositories are obsolete and may be deleted. Do not fetch, build from, import from, or rely on them for current development; use this repository's source and history instead.
- **Selected software:** retain explicitly approved improvements and applications from previous work, including **9pterm** (the host-native, nongraphical drawterm variant), corrected host-native drawterm, browser-based drawterm where its required bridge is understood, and WireGuard as a later independent task. **Host applications are not 9front user programs**: keep their complete source and host build under a separate auxiliary application area outside the assembled 9front OS tree. The host-native 9pterm build uses host `cc`, `GUI=none` and `-DNINEPTERM`; maintain the implementation in this repository. Host GCC/cc is permitted for these host tools and existing build helpers; this does not change 9front's native compiler model. Do not import unrelated experiments or duplicate one application under multiple names.

The old separate `userland` repository, the experimental GCC integration, and the separate custom Plan2001 source-tree architecture are **obsolete** and must not be reintroduced. Preserve the 9front compiler/toolchain model and the working WASM32 port. The host tools used to produce an existing EFI binary do not justify adding a GCC-based Plan2001 userland.

## Architecture

### One 9front source tree

Keep 9front's original directory layout and its native abstractions. Architecture-specific files and approved enhancements belong in their natural 9front locations. Do not reorganize the system into parallel `kernel/`, `userland/` and `web/` operating-system trees.

**Source assembly:** `tools/tree` takes the locked commit's files from the upstream cache (`$PLAN2001_CACHE/9front.git`, default `$HOME/.cache/plan2001`; fetched on first use, the tree SHA verified), applies `patches/9front/series` and overlays this repository's new files, then applies the approved source reduction (`tools/prune-tree`). Every change to an upstream file is a patch, the single source of truth for that file: each names the exact blobs it applies to and produces, so a changed upstream file, fuzz, offset or failed hunk stops the assembly. A tracked file at an upstream path, a pruning edit whose expected text is missing, or pruning that removes a patched or Plan2001 file also stops it. `patches/9front/series` orders patches deterministically (several may change one file) and classifies each (general fix, upstream backport, WASM32, UEFI, integration) with its upstream status; `patches/9front/README` says what each does. Updates are three-way (old upstream, Plan2001's change, new upstream); a conflict is resolved by editing the merged file, never by replacing the new upstream file with an old copy. A patch is dropped only when upstream already makes the identical change. Local fixes that are general 9front bugs are candidates to offer upstream, only with the owner's consent. The assembled tree is the source used for every target (WASM32 host build, native VM builds, the tree branch and distributions). A failed fetch or mismatched cache is a build-environment blocker, never bypassed with an unverified or different 9front. One repository: no second fork or separate upstream repository to maintain.

**Bootstrap:** native targets are built in a 9front QEMU VM (`~/.cache/plan2001/base.qcow2`) whose first compilers come from the lock's SHA256-verified bootstrap release (`BOOT_ISO`, currently 9front-11952). `tools/native-amd64/build` compiles the whole locked `/sys/src` with them, then rebuilds everything (9front's own release recipe) with the compilers it built; the shipped kernels, libraries and programs, the ARM64 and Pi4 builds' toolchain and the image tools all come from that build. The bootstrap release also supplies the Raspberry Pi firmware blobs that upstream fetches from a moving branch; nothing else of it is shipped.

**Port boundaries:** share the `sys/include/bootinfo.h` ABI and `sys/src/9/port/bootinfo.c` validation/runtime logic. Keep CPU entry, early physical mappings, framebuffer mapping and device access in architecture-specific code. Maintain the native EFI loader, necessary AMD64 early-boot routines, BootInfo integration, boot-argument handling and framebuffer progress markings in this repository. Do not import GE/O-modified kernels, separate userlands or unrelated experiments. For AMD64, retain upstream's `pc64` driver configuration as the baseline (plus narrowly necessary BootInfo and UEFI integration), preserving 9front's device model and its `#l`, `#I`, `#W`, IPv4/IPv6, ARP, networking, storage and userland services. The archived GE/O O-only configuration is not an approved driver-pruning source: it removes the 9front network stack. Defer any 9front-compatible driver pruning to a separate owner-approved change. Do not indiscriminately delete drivers.

Current native targets are AMD64 and ARM64. WASM32 is another **native 9front architecture**: its 9front user-space applications are compiled to and execute as WebAssembly. It is **not** a Linux userland, a Linux syscall compatibility layer, a container, or a Linux-like userspace port. The target list must not be confused with an assertion of present feature parity.

**Approved source reduction:** the assembled OS source tree, target builds and installed distribution exclude Ghostscript (`sys/src/cmd/gs` and its exclusive resources), APE (its headers, libraries, wrappers and tests), and CPU targets other than AMD64, ARM64 (including bcm64/Pi4) and WASM32. RISC-V64 remains an optional future target only; no implementation or release work is required. Keep the locked upstream source intact in the cache and the bootstrap VM; apply this reduction deterministically when assembling Plan2001. Keep required shared compiler/linker code, native libc and C preprocessor, architecture transition assembly, supported-target drivers and host-native auxiliary tools. Ghostscript-dependent PDF/PostScript viewing, conversion and printing may be removed; keep image viewing and other independent functions. Programs that require APE may also be removed; retain APE-independent programs from the same source directories and preserve their build paths. Preserve all other software and functionality. Do not restore removed components as an incidental compatibility fix.

### One boot contract, minimal platform-specific loaders

The shared contract between loader and kernel is **BootInfo v1**, retaining the ABI and working WASM32 interpretation maintained in this repository. One common header and one common C implementation own BootInfo layout, parsing, validation and version compatibility across targets. Preserve the shared validator and its strict compatible checks (section bounds/overlap, architecture, memory types, root image, framebuffer, optional FDT and entropy). No architecture may maintain a divergent private copy of shared validation. Preserve the already existing `port`↔architecture function interfaces and signatures: `bootearlymap(uvlong, uvlong)`, `bootinfoinit()`, `bootinforandinit()`, `bootinfoclock()`, `bootmem(int)`, `bootmemclass(u32int)`, `bootconfig()`, `bootfdt(ulong*)`, `bootargsinit()`, `getconf(char*)`, `setconfenv()`, and the ISA-specific `BootInfoArch` constant. Architecture-specific functions remain architecture-specific; do not move them into the shared parser.

BootInfo v1 is append-only: missing optional trailing fields mean zero/absent, and incompatible layout or semantics require a new ABI version. The legacy GE/O boot-process manifest is **not** part of the 9front boot model. Its optional trailing fields may remain accepted for binary compatibility, but the 9front kernel must neither require nor execute the GE/O process graph. `plan9.ini` remains ordinary 9front configuration data.

**Native machines:** keep the modern UEFI-only loader and boot behavior maintained in this repository. Keep local EFI/ESP boot of installed systems, including current GRUB-assisted boot where needed. Do not restore legacy BIOS/9boot as active native boot routes. Integrate and adapt the existing native EFI loader instead of designing another loader. It already handles 9front a.out kernels and a restricted ELF64 path; **retain both initially**, with 9front a.out the primary native kernel format. An ELF implementation useful to the existing loader is not grounds to restore the abandoned GCC-based OS/userland. The native target build uses 9front's `mk`, appropriate compiler/assembler/linker (`6c/6a/6l` for AMD64) and `aux/aout2efi`. The existing Linux `tools/hostcc/build` only produces `3c/3l/3a` for WASM32; **it is not an AMD64 toolchain**. Native AMD64 compilation runs in the bootstrap 9front QEMU VM with those tools, rebuilt from the locked source, while Linux hosts prepare and boot the resulting artifacts. A dedicated, isolated native host-toolchain solution may be introduced later, without modifying WASM32's toolchain in parallel. The existing optional host-GCC EFI path may be kept separately for compatibility but must not make GCC the target OS toolchain. The imported EFI source may retain shared and ARM64-specific files unchanged, while AMD64 alone is built and validated in the first milestone.

Existing legacy boot source files may remain as unused upstream source, but must not be selected by new native build, boot or installer configurations. Preserve the working WASM32 `inst/bootsetup` behavior and its existing `patches/9front/inst-bootsetup-9fat.diff`. Do **not** independently edit that shared patch or its overlaid `rc/bin/inst/bootsetup` during parallel AMD64 work. Provide a separate AMD64 ESP/raw-image generator as a first delivery, with installation using that bootable image. Any later shared installer integration is a single integrator-owned change made after the WASM32 foundation has landed.

Extend the loader for network boot rather than replacing it. The proposed UEFI HTTP Boot flow is: firmware obtains a small Plan2001 EFI program; that program loads the kernel and required boot materials over the network and enters the kernel using BootInfo. Firmware compatibility and transports must be handled explicitly; do not assume every firmware can perform HTTPS or HTTP Boot reliably.

**Browser/WASM32:** keep its existing small web bootstrap, **not a full UEFI firmware emulator**. JavaScript may assemble the binary BootInfo v1 blob and use browser facilities to fetch and instantiate WebAssembly, initialize shared memory and provide devices. Its C kernel consumes the same BootInfo layout and shared validation as native targets; the browser need not run the native EFI C program. WASM32 boot does not require GPT or ESP. Preserve the working WASM32 runtime, UI, Web Workers, canvas, touch interfaces and installer behavior. Keep the browser-specific boundary thin and explicit.

**Native implementation order:** complete AMD64 on UEFI first. ARM64 starts with QEMU `virt` under UEFI and its BootInfo pointer in `X0`; later hardware platforms (including Raspberry Pi) are distinct follow-up work. RISC-V64 is an optional future port, not an existing upstream port or a scheduled milestone. If separately approved later, its proposed first platform is QEMU `virt` with UEFI and a BootInfo pointer in `a0`. The ABI and intended targets do not imply these ports are already bootable.

**ARM64 loader platform contract:** select `efiplatform=qemu-virt` or `efiplatform=rpi4` explicitly. QEMU retains upstream's headed 9front a.out path for the board. Pi4 requires a linked AArch64 ELF64 ET_EXEC image with explicit physical load addresses and matching virtual addresses, plus `efibootmap=base,length` and `efiscratch=base,length` describing the kernel's actual early mapping and writes outside its load segments. Raw `-H6` images, relocation guesses and arbitrary firmware DTBs are not part of this contract. Validate the complete image and BootInfo placement against UEFI memory descriptors before writing image bytes; retain resident firmware and reserved memory. This loader contract does not implement Pi4 kernel relocation, PSCI or hardware support. BootInfo v1 and its X0 handoff remain unchanged.

The purpose of this unification is a common kernel hand-off and maintained source code, **not** binary-identical firmware on fundamentally different execution platforms.

### Boot source is chosen explicitly

The user chooses what to start. Opening a URL starts that URL's system; selecting a local server or launching an installed offline PWA starts that environment. Do **not** automatically redirect to a different origin, choose another operating system, or silently fall back to an unrelated boot source when the requested server is unavailable.

## Distribution, installation and offline use

- **Web:** `plan2001.com` hosts the browser-bootable WASM32 system. The same application must be usable through a local HTTP server (including `tools/serve`) and as an explicitly launched offline-capable installed PWA. A bare `file://` HTML launch is not required.
- **Browser storage:** retain the functioning OPFS-based installed system. OPFS is scoped to the page's origin: separate origins do not share an installation implicitly. The offline PWA explicitly caches the boot resources an installed system needs to start without network: the page and `platform.js` (with the manifest's icons), cached completely per version and replaced only by a complete newer version; the installed system's firmware, kernel and root come from its OPFS disk. The network live image and its ISO are not cached, so they remain network-only; offline, such a boot fails visibly instead of starting something else.
- **Native network boot:** prefer UEFI HTTP Boot when supported and reliable. The EFI first stage may retrieve the kernel and boot resources from `plan2001.com`. Prefer HTTPS, but do not treat HTTPS alone as a substitute for authenticating boot artifacts. Before enabling public network boot, require a trusted signature on an authenticated boot manifest that identifies and hashes the exact kernel and boot resources, with verification anchored in a key provisioned independently of the downloaded manifest. Plain HTTP may only carry payloads when this signature policy is enforced. Keep UEFI Secure Boot as a distinct, separately designed feature. On missing, invalid or untrusted boot artifacts, fail with a clear diagnostic, without silently booting a different source. Network boot must not break local UEFI boot.
- **Native installation:** initially, an architecture-specific UEFI-bootable raw disk/USB image is sufficient: ESP, EFI loader, kernel and required 9front system files. A live environment may load its installation payload directly from the server or from an explicitly downloaded package. Once installed, a native system must boot from its own disk without network access, using the existing UEFI/ESP mechanism. A new package manager is out of scope for boot consolidation.
- **Removable media:** if required, distribute the simplest practical UEFI-bootable raw USB disk image, architecture-specific when simpler. A single multi-architecture image is not mandatory.
- **ISO 9660/CD-ROM:** not a design requirement or preferred **new** native distribution format. **Preserve the currently working WASM32 ISO/live-image loading, `?iso=file` path and installer workflow.** Do not build new architecture around ISO, CD boot, PXE legacy paths or historical installer assumptions. The old ISO workflow and the new ISO-independent distribution goal can coexist during migration.

## Accounts and passkeys

Plan2001 accounts are genuine 9front users, created by invitation and used with WebAuthn passkeys instead of typed passwords.

- **Separate concerns.** Authentication (a passkey assertion), invitation authorisation (who may create which account and join which groups), session issuance, network permission (`aux/ethernetd` accepts a browser machine's link only for a live session) and file access (a genuine dp9ik login as the user) are separate decisions. Holding one never implies another.
- **Server-side verification** lives in one library, `libwebauthn` (`sys/include/webauthn.h`), used by `auth/accountd`. There is one account system: `aux/ethernetd` keeps no passkeys, invitations or accounts of its own. It accepts only ES256 (P-256) keys, requires user presence and user verification, and checks type, challenge, origin, cross-origin use, RP ID hash, backup flags and the signature counter. Attestation is `none`; attestation statements are not verified.
- **Explicit RP and origins.** `auth/accountd -r RPID -o ORIGIN...` names the relying party and its origins, and the page's `p2-rpid` meta must match. RP IDs are not interchangeable: `auth.plan2001.com` and `plan2001.com` passkeys are different credentials, and a deployment chooses one deliberately.
- **Provisioning.** An invitation (`auth/account invite NAME TTL [GROUP...]`, its code shown once and stored hashed) fixes the account name and its groups. Enrolment creates, under one lock: the account record, a random dp9ik key in keyfs (no one knows it as a password), the file server user and home (`newuser` on the file server console), group memberships from the allowlist (`-g`), and the passkey record, which is exclusive to one account. A failure undoes the keyfs entry, groups and passkey and leaves the invitation unused; a file server user that the console cannot remove is adopted by a retry. Names are `[a-z][a-z0-9]{1,26}`; reserved system names and existing users are refused, and groups never include users' own groups or names outside the allowlist.
- **Passwordless.** Enrolment and sign-in need only a passkey, with or without PRF. An account may have several passkeys (this device, a phone through the browser's hybrid/QR flow, a security key); a user cannot remove the account's last passkey. **Another device** joins an account without moving a passkey: the signed-in device shows a one-time HTTPS link (a QR code, its code in the URL's fragment, 5 minutes), the new device claims it once, both show the same 6-digit number, the signed-in device approves with one of the account's passkeys, and the new device makes its own passkey with whatever provider it uses and gets a session (`auth/accountd`'s `pair` requests). Sessions are random bearer tokens, kept only as hashes in `auth/accountd`'s memory with an absolute expiry. Adding a passkey needs a recent sign-in, and revocation, sign-out or disabling an account ends the affected sessions.
- **File access.** A passkey assertion never authenticates a 9P attach by itself. The host owner's broker `auth/asuser` turns a session into its user with a genuine dp9ik exchange: a private factotum holding the user's keyfs key authenticates to the host owner's factotum through the auth server, and the resulting capability makes the process the user (`auth_chuid`) in the user's own namespace, where the file server checks permissions as for any user. The host owner's privileges are never used for the user's I/O.
- **Page.** `sys/lib/accounts` is the reusable client. It connects only to its own origin's `/account` WebSocket (`aux/etherws -C`), takes the invitation from the URL fragment, and keeps the session in a `SameSite=Strict` cookie (`Secure` on HTTPS).
- **Session checks without keys.** A host-owner service that only needs to know whose a session is (`aux/ethernetd`, Room's control plane) asks `auth/accountd` `session TOKEN` and gets the active account's name, never its key.
- **Native logins** (drawterm, rcpu) still need a password. A passwordless account has only a random key, so it reaches the system through the broker unless an administrator also sets a password.

## Browser applications on a server's files (WASM32 application mode)

A web application such as Room is a **Plan2001 user program running on a real WASM32 Plan2001 machine in the browser**, with an HTML/JavaScript user interface. It is not a web application with a messaging backend: there is no data API, database or second protocol; the server's native file server is the data.

- **Application mode.** The page boots the current WASM32 kernel with a minimal boot file system (`sys/src/9/wasm32/app.proto`, `app.fs` in the live image) and `init=/bin/rc /boot/app`: no Rio, console window or disk. `/boot/app` brings the network up (DHCP on `#l0`) and runs `aux/jsio`. The full Rio system (`kernel.html`, `bootfs.proto`) is unchanged and separate.
- **JS–native file interface.** `#j/js` (`devjs.c`) is a message channel between the page and one native server, `aux/jsio` (`sys/src/cmd/jsio`), which performs the page's requests as ordinary system calls in the machine's namespace: stat, open, create, read, write, dirread, close, remove, wstat (rename, group, mode), bind, mount and unmount, with bounded (64 KiB) data per message, concurrent requests and binary data. `jsfs.js` is the reusable asynchronous JavaScript client (readdir, readFile, writeFile with atomic publication by one `fwstat`). The page never implements a file system or 9P: remote files go through the kernel's own 9P, TCP/IP and Ethernet. Rename, group and mode changes are native `wstat`s, permission checks the file server's.
- **Network and identity.** The machine's Ethernet is a WebSocket to its own origin's `/ether` (`aux/etherws`, `aux/ethernetd`). The first message is the page's `auth/accountd` session (`session TOKEN`); `aux/ethernetd` checks it with accountd, gives the machine an address on 100.64.0.0/24 and checks the session again every minute: logout, expiry, revocation or a disabled account end the link and its file service. A session is network permission only.
- **File service.** TCP from a machine to its gateway's port 564 reaches the server's stack; `aux/ethernetd` serves the call with `exportfs` as the machine's account, started by `auth/asuser` with that session (a genuine dp9ik exchange, the user's own namespace; never the host owner's). A required export pattern (`-x`) limits what is exported (Room: `/usr`, `/adm/users`, `/adm/room/rooms`; without one the user's whole namespace, `/net` included, would be exported); the file server's owner and group permissions decide the rest, so a native rc or Drawterm write and the browser see the same files. One long-lived mount per page, at most four exports a machine and one new call a second (four at once), hung up with its link. A group change (membership revocation) applies at the next open; a removed member cannot read even within an established session.
- **No routing beyond the server.** Without `-e` a browser machine reaches only this file service: not the Internet, the WireGuard administration network or other services. `-e` restores the historical restricted egress (TCP 80, 443, 9418, DNS to fixed resolvers) and is not used for Room.
- **Change hints.** An optional private native 9P service is mounted by `aux/ethernetd -E /srv/SERVICE` after `auth/asuser` changes identity, at `/n/events`, and exported through the existing restricted mount. Only the host owner opens the raw service pipe; the service may trust local kernel-generated attach identities only while that pipe stays private. JSFS `wait(fid, offset, count)` performs an ordinary blocking read in a bounded separate JSIO process, holding a duplicate descriptor until completion; cancel through the service before closing the fid. No kernel, CWFS, 9P protocol or extra WebSocket mechanism is required. Room documents its event and control files, canonical reaction records and private monotonic read cursors in its own root README. External writers may explicitly signal invalidation; otherwise their writes appear on open, resume, reconnect or refresh.
- **Assets.** `9wasm32.wasm`, `app.fs`, `platform.js` and `jsfs.js` (and their `.gz`) are served versioned (`?v=`) and cached; the page is cross-origin isolated (COOP/COEP) for the machine's shared memory. Files read are cached only in memory; the server's files are authoritative.

## Network access and administration

A public Plan2001 server exposes its web service and nothing else. Native administration (auth 567, rcpu 17019, 9P 17020) is reached only through Plan2001's own WireGuard tunnel, and dp9ik authorisation still applies inside it.

- **WireGuard is `#W`** (`sys/src/9/ip/devwg.c`), Plan2001's own implementation of the protocol (Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s, libsec's crypto) as the IP medium `wg`; not a port of Linux's driver. `ip/iproute.c` adds `v4lookupskip`/`v6lookupskip` so that the tunnel's own outer packets never route into a `wg` interface (`patches/9front/iproute-lookupskip.diff`). The device's ctl and status are described at the top of `devwg.c`.
- **Public IPv4:** only WireGuard (UDP 51820) and necessary ICMP. **Public IPv6:** HTTPS (TCP 443) for the site, Room and WASM32, HTTP 80 only for certificate renewal, and ICMPv6. Native service listeners are bound to the tunnel address, never to a public one; the cloud firewall restricts the same ports independently.
- **Administrators:** one key and one /32 per client in 10.201.0.0/24 (server 10.201.0.1, silli .2, kuha .3), split tunnel to the server only. Clients are authenticated by key, not by source address, and may roam. Private keys are made on the machine that uses them and never leave it.
- **Server:** `wgsetup init 10.201.0.1 255.255.255.0` once (new private key, `/adm/wg/wg0`, host owner only), `wgsetup up` at boot (from `/cfg/$sysname/cpustart`), `wgsetup peer NAME ADDR KEY` and `wgsetup remove NAME` take effect at once and persist in `/adm/wg/wg0.peers`, `wgsetup show` for the public key and counters. Then `aux/listen -q -a 10.201.0.1 -t TRUSTDIR -d SERVICEDIR tcp` serves the native services on the tunnel only. Local auth clients (Room's broker, factotum) find the auth server through `ndb`: `auth=10.201.0.1` for the authdom. Never put the tunnel address as `ip=` on the machine's own `ether=` entry: `ipconfig` would configure it on the Ethernet interface at boot instead of DHCP, and `wg0` would not be bound.
- **Linux client:** `tools/wg-admin init NAME ADDR` (prints the `wgsetup peer` line), the server's public key in `~/.config/plan2001/wg/server.pub`, then `tools/wg-admin up` and `9pterm -h 10.201.0.1 -a 'tcp!10.201.0.1!567' ...`. `ip/wgkey` makes and derives keys on Plan2001.

## Preservation and scope

1. Do not replace a working component merely to make the architecture look cleaner.
2. Keep existing 9front behavior except where a change is explicitly specified here.
3. Preserve upstream's complete pc64 driver configuration and kernel network services. The former GE/O-only driver reduction is not approved for 9front; evaluate driver pruning only as a separate future task.
4. Preserve the mobile Rio touch semantics, text selection, Android keyboard handling, fullscreen behavior, display, and existing browser UI **unchanged** through the boot migration.
5. Migrate only approved programs and improvements; do not automatically import whole obsolete repositories.
6. Preserve 9front's existing network protocols and user-space behavior, including older authentication or remote-access mechanisms, unless a distinct approved change removes them; protocol retirement is not part of the boot migration.
7. Preserve working native EFI boot diagnostics: the loader's framebuffer stage marks before and after ExitBootServices and before kernel transfer, with kernel-side marks continuing the same row. These marks and `[P2 Lxx]` output are troubleshooting signals, not substitutes for successful boot.
8. This document defines architecture and scope. Implementation, CI additions and new test campaigns are separate subsequent work, not prerequisites for writing this specification.

### Integration acceptance

- The initial native AMD64 path is accepted only when UEFI firmware -> Plan2001 EFI loader -> valid BootInfo v1 -> **9front AMD64 kernel -> 9front init -> usable 9front userland** works, including an installed offline UEFI/ESP boot. Loader messages or coloured framebuffer marks alone do not meet acceptance.
- The existing WASM32 build and browser boot must remain functional, including its existing UI, process execution, Rio input/touch semantics, OPFS and ISO/live workflow.
- Use GitHub Actions for repeatable targeted builds and smoke/integration tests; run local or real-target checks only when needed. For QEMU KVM with TCG fallback use `-machine accel=kvm:tcg` (or `-accel kvm -accel tcg` where supported), **not** `-accel kvm:tcg`. Include OVMF for AMD64 UEFI tests and Chromium for browser tests. Do not commit diagnostic artifacts. GitHub Actions runs focused builds and functional checks.
- ARM64 is a current target: validate QEMU virt boot and bcm64/Pi4 builds locally. RISC-V64 is optional future work and is excluded from current build, release and acceptance requirements.

## Operating plan2001.com

The procedure that works today, run from the administrator's Linux host (Kuha). Secrets stay on that host and are never committed; only their paths are given.

**Host prerequisites:** OCI CLI at `~/.local/bin/oci` with `~/.oci/config` (API key `~/.oci/oci_api_key.pem`); 9pterm at `~/bin/9pterm` (build: `tools/clients/drawterm/build.sh 9pterm`); plan9port at `~/plan9port` (WASM32 build); this repository and `plan2001-kernel/room` checked out side by side (`~/Src/plan2001`, `~/Src/room`). Native builds put large temporary files in `TMPDIR`; `/tmp` is a small tmpfs, so use `export TMPDIR=~/.cache/plan2001/tmp`.

### Oracle Cloud

### Deployment

Always build from current `main`. Keep the previous version of everything replaced.

1. **Native AMD64:** `tools/native-amd64/build --out ~/.cache/plan2001/NAME/deploy` (kernel `9pc64` with the boot file system's cwfs, `root.tar`). A build that stops on lost serial input can simply be run again. Optional check: `tools/native-amd64/mkimage --in …/deploy --out t.img --disk sd00 --console 0`, then `NINEPTERM=~/bin/9pterm tools/native-amd64/boottest --image t.img --disk sd00 --bus vscsi:s0:0:1` (Oracle-like virtio-scsi root).
2. **Native programs** (accountd, asuser, ethernetd, etherws …): extract them from `root.tar` (`tar xf root.tar amd64/bin/auth/accountd …`), `put` them to `/tmp/d`, copy the old ones to a backup directory (e.g. `/usr/glenda/bakDATE`), `cp` the new ones over `/amd64/bin/…` (cp keeps the target's mode). They take effect at the next restart (above).
3. **Kernel** (only when it changed): mount the ESP with `dossrv -f '#S/sd00/esp' espX; mount -c /srv/espX /n/esp`, then `cp /n/esp/efi/plan2001/9pc64 /n/esp/efi/plan2001/9pc64.preDATE; cp /tmp/d/9pc64 /n/esp/efi/plan2001/9pc64`, check with `md5sum`. plan9.ini is `/n/esp/efi/plan2001/plan9.ini`. Then restart.
4. **WASM32 browser firmware** (Room's browser machine): `PLAN9=~/plan9port tools/build` writes `build/live/`. Deploy `9wasm32.wasm`, `app.fs`, `platform.js`, `jsfs.js` and their `.gz` files to `/adm/room/web/wasm/`, and write a new `/adm/room/web/wasm/version.txt` (any new string, e.g. the first 16 hex digits of a sha256 of those files). The page loads the firmware as `?v=VERSION`, so a new version is what makes browsers and installed PWAs fetch it; `platform.js` carries its own SHA-256 stamp (`tools/platstamp`), so never edit a built copy by hand. No restart is needed.
5. **Room** (`plan2001-kernel/room`, its README "Asennus plan2001.comiin"): `web/*` → `/adm/room/web/`; `native/`: `mk install` on the server (roomctl, roompush, roomfront), `native/room.export` → `/adm/room/export`; `deploy/plan2001.com/start` → `/adm/room/start`. roomctl/roomfront are started per connection by `tcp443`, so new copies apply to the next request; changes to accountd, ethernetd or `/adm/room/start` need the restart.
6. **Verify:** `curl` returns 200 for `https://plan2001.com/`, `/room/` and `/room/wasm/version.txt` (the new version); over 9pterm, `ps` shows cwfs64x, accountd and ethernetd, `md5sum` of the installed files matches the build, and `tail /adm/room/ether.log` shows a machine `up as 100.64.0.N` with bytes going both ways. Then open Room on a phone. A manual push test: `roomorigin=https://plan2001.com /bin/roompush send ROOM SENDER message >>/adm/room/push.log >[2=1]` (glenda is a member of room Klassikko, `8efa067e2feaa0b1`, for tests; a user's own messages never notify that user's devices).
